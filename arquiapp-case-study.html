ArquiApp: from 30 WhatsApp groups to one record

An architecture studio was running site reporting through dozens of WhatsApp groups. I mapped how the work really flowed, listened when my first design missed the mark, and redesigned the process so nobody on site had to change how they work.

By Nicolás Martelli · 7 min read

At a glance

Client
An architecture studio in Argentina and Uruguay with more than 10 active building projects
My role
Business analysis, process design and build, end to end
Methods
Stakeholder interviews, BPMN process maps, user stories with acceptance criteria, a success metric with a baseline, an evaluation set for the AI
Stack
Next.js, Supabase (PostgreSQL), WhatsApp Business API via Twilio, speech-to-text, Claude

1. The problem

Every project had three WhatsApp groups: one with the client, one inside the studio and one with the builder. With more than 10 projects, that meant over 30 groups where everything landed together: progress updates, photos, payments, client questions, and what had been approved or changed.

Finding anything meant scrolling and filtering by hand. Four things were being lost:

  • Time: the studio director spent hours chasing and sorting information.
  • Early warnings: problems surfaced late, which meant rework and delays.
  • Client trust: clients were not always well informed.
  • A record: no reliable history of what was approved, what changed and who decided, which matters most when there is a dispute.

2. Agree on success before building

Before designing anything, I set one number to judge the project by: the share of active projects with a report in the last three working days. At the start it was 40%: fewer than half the projects had a recent report. The target is 80% after four weeks of use. Every feature that followed had to move it.

4. My first design, and what the stakeholders taught me

Version one was app-first. Foremen and architects would record voice notes in a mobile web app, AI would turn each one into a structured report, and the studio partners would follow every project from a dashboard. It worked in testing.

Then the studio director pushed back. Foremen work for the builder, not the studio, and other people involved would not install or open a new app. WhatsApp was how they already worked, and asking them to change would kill adoption. What the director wanted from the dashboard was reporting, reminders and a WhatsApp integration, not a new place for people to type.

Version one: app-first

  • Foremen log in and record in the app
  • Partners manage everything in the dashboard
  • Adoption depends on everyone changing habits

Version two: WhatsApp-first

  • Site teams and clients keep using WhatsApp
  • An assistant number sits in each project group and reads along
  • The dashboard is the reporting and control layer

The lesson: design around the behaviour people already have. A feature nobody uses moves no metric.

5. The redesigned process (to-be)

Three design rules came straight from the stakeholder conversations:

  • Raw first. Every message is stored exactly as it arrived, so it can be reprocessed when the AI improves and it doubles as the record for disputes.
  • One question at a time. When the assistant is unsure which project a message belongs to, it asks the director a single question with numbered options.
  • Nothing goes out unapproved. Every reminder is a draft until the director replies 1, 2 or 3. During testing, the assistant can only message an approved list of numbers.

6. User stories and acceptance criteria

1. Capture what happens in the groups

As the studio director, I want the assistant to read each project's WhatsApp groups so that updates land in the right project as structured reports, without anyone forwarding anything.

  • GIVEN a foreman posts a voice note in a project group, WHEN it is processed, THEN a report appears under that project with work done, problems, missing items, next steps, and approvals or changes.
  • GIVEN a message is unclear, WHEN the assistant processes it, THEN it asks me one question with numbered options and waits for the answer.

2. Spot silent projects

As the studio director, I want to see which projects have gone quiet so that I can follow up before small issues grow.

  • GIVEN an active project without a report in the last three working days, WHEN I open the dashboard, THEN it is flagged as "no report for X days".
  • GIVEN the end of each day, WHEN the daily job runs, THEN the success metric is calculated and stored.

3. Approve every reminder

As the studio director, I want to approve reminders before they are sent so that nothing goes to my team or clients without my say.

  • GIVEN a drafted reminder, WHEN I reply 1, 2 or 3, THEN it is sent, sent back for a new text, or dropped.
  • GIVEN test mode is on, WHEN a message targets a number outside the approved list, THEN it is blocked and logged.

4. Chase client decisions

As the studio director, I want clients to be reminded about pending decisions so that work does not stall waiting for them.

  • GIVEN a client decision is still pending, WHEN three working days pass, THEN a reminder is drafted for my approval.
  • GIVEN a topic has already had three reminders, WHEN it is still pending, THEN no further reminders are drafted.

5. Start the day with a summary

As the studio director, I want a short morning summary on WhatsApp so that I know what needs attention without opening every group.

  • GIVEN it is morning on a working day, WHEN the summary job runs, THEN I receive overdue tasks, client items pending for days, and items to review.

7. The app

The dashboard is where the director starts the day: overdue tasks, what clients still owe a decision on, invoices to pay, and every active project with how long it has been since its last report. The screenshots below use invented demo data, so no real project, client or person appears.

8. Where it stands

The app is being piloted with the studio: reports, the project dashboard and invoice tracking run in production, and the WhatsApp assistant is in testing. The next step is the one that matters: tracking the success metric for four weeks against the 40% baseline.
